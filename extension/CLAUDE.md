# DokHack (독해크)

Chrome/Whale MV3 extension: sentence mining for Korean speakers reading English (Kimchi Reader in reverse). UI copy is Korean; code and comments are English.

## Commands
- `npm install` then `npm run build` → outputs to `dist/` (load unpacked in chrome://extensions or whale://extensions)
- `npm run watch` for dev; reload the extension card + refresh the tab after changes
- `npm run typecheck` before finishing any change
- Review website: `cd ../web` — separate project, its own README/setup. Both `src/config.ts` files (here and in `../web`) need the same Supabase project URL + anon key before account sync works; see `../web/README.md`.
- Landing page: `cd ../landing` — separate project, no build step (plain HTML/CSS), same Cloudflare Workers deploy pattern as `../web`; see `../landing/README.md`.
- `static/krdict.json` (~7.6 MB, the local English→Korean gloss data) is a committed build artifact, not hand-written. Regenerate with `node scripts/extract-krdict.mjs <path to unzipped KRDICT dump>` — see that script's header comment for where to get the dump and the full story on why it exists.
- `static/wordnet.json` (~15.7 MB, the local English definitions) and `static/phrases.json` (~140 KB, the phrasal-verb/connector match list) are also committed build artifacts, both produced by the same script, which also folds in `scripts/connectors.mjs`'s hand-curated discourse connectors. Regenerate with `node scripts/extract-wordnet.mjs` — no download needed, it reads from the `wordnet-db` devDependency (bundled WordNet 3.1 data files).
- `extract-krdict.mjs` also tops up `krdict.json` with `connectors.mjs`'s Korean glosses, but re-running it needs the KRDICT bulk dump again (see that script's header) — the copy used to build the current `static/krdict.json` is gone, so that specific top-up was last applied as a direct one-off patch to the built JSON, not a full script re-run. If you re-run it from a fresh dump, the connector entries it adds should end up identical.

## Architecture (keep these invariants)
- Never modify page DOM for highlighting. Use CSS Custom Highlight API (`::highlight(mine-unknown|mine-learning)` in static/content.css); click hit-testing via caretPositionFromPoint in content.ts.
- NLP (wink-nlp, ~3 MB) runs ONLY in the background service worker. Content script sends text batches via `{type:'tokenize'}`. Keep content.js as small as reasonable (currently ~32.5 KB, most of it the card editor UI plus youtube.ts below — the popup+editor pair was the ceiling before that, still comparably small). `static/krdict.json` (~7.6 MB), `static/wordnet.json` (~15.7 MB), and `static/phrases.json` (~59 KB) are each fetched lazily by the background worker on first use and cached in memory — none are ever bundled into content.js or background.js's own parse size.
- Phrasal verbs, verbal idioms, and discourse connectors ("give up," "turn a blind eye," "as a result" — roadmap item 4) are merged into a single token at tokenize time: `nlp.ts`'s `mergePhrasalVerbs()` looks up each token's lemma in `phrases.json` (built from WordNet's own multi-word verb *and* adverb entries, plus `scripts/connectors.mjs`'s hand-curated top-up for connectors WordNet doesn't have at all — "as a result" isn't in any WordNet index) and, if the following tokens match a known phrase and are truly adjacent (nothing but whitespace between them — punctuation blocks a merge), collapses them into one token with a space-joined lemma. Each phrase entry carries which class it is ('v' or 'r'), and the head token's actual POS must be compatible (VERB/AUX for a verb phrase; ADP/ADV/SCONJ for a connector) before a merge is attempted — otherwise a NOUN "look" in "a good look up close" would wrongly merge with the verb phrase "look up" (found by testing). That merged lemma is looked up in `wordnet.json`/`krdict.json` exactly like any single-word lemma — no changes needed to `wordnet.ts`, `krdict.ts`, highlighting, click hit-testing, or word-status storage, since none of them assume a lemma is one word. This handles the *contiguous* case; a split phrasal verb ("turn the lights off") is a separate match attempted right after a contiguous one fails, `nlp.ts`'s `findSplitParticle()` — a cheap bounded heuristic rather than real dependency parsing (which would place the object properly but which wink-nlp doesn't have): only tried for a genuine two-word verb-phrase entry (a longer idiom like "turn a blind eye" has a fixed object that *is* the idiom, not a free slot to split around, so it's never attempted there), it scans up to `MAX_SPLIT_GAP` (4) tokens past the head for a token whose lemma matches the entry's particle, requiring every token in between to be a plausible bare object noun phrase (DET/ADJ/NOUN/PRON) with no punctuation anywhere in the run — a conjunction, another verb, or a comma in the gap stops the scan immediately rather than risking a merge across clauses. Since there's no single contiguous `Range` that could cover "turn ... off" while excluding "the lights" in between, only the verb token's own lemma is rewritten to the phrasal form (its Range/surface stay just that one word); the particle token is dropped from the output entirely (consistent with it not being independently clickable in the contiguous case either), while the object words in between are left as ordinary, independently-tracked tokens, completely unaffected. Verified directly against real wink-nlp + the real built `phrases.json` (not just reasoned about): "turn the lights off" → "turn off" + independent "the"/"light"; a 4-word object noun phrase right at the `MAX_SPLIT_GAP` boundary ("pick the old blue jacket up") still merges, one word past it doesn't; a comma or a conjunction in the gap correctly blocks the merge; "turn a blind eye to it" correctly never attempts a split merge at all. Since tokenizing now happens per block (see the next bullet), a phrase split only by inline markup ("give <em>up</em>") *is* still caught — "adjacent" is checked in the block's flat text, where markup contributes no characters. Phrase words are lemmatized at extraction time too (`extract-wordnet.mjs`'s `lemmatizeWord()`) — WordNet's own stored form is sometimes inflected ("call_the_shots," "in_other_words"), which would otherwise never match a real sentence's already-lemmatized tokens ("shots" → "shot") and silently never merge; found by testing "in terms of," fixed for that and ~80% of similarly-affected entries (the rest involve a possessive "'s," which `tokenize()` drops as a contraction piece anyway and so can't merge regardless — see roadmap item 4).
- Tokenizing happens per block-level element, not per text node (`highlighter.ts`'s `Highlighter`, keyed by `Unit = Element | Text`): `blockOf()` finds the nearest non-inline ancestor, all its non-excluded descendant text nodes' data are concatenated into one flat string, and that whole string is sent to `tokenize()` together — so "I <b>really</b> like it." reads as one sentence, and even a word split mid-word by markup ("un<b>believable</b>") reassembles correctly, instead of each text node being tagged in isolation. A resulting token's highlight `Range` can legitimately span multiple text nodes (the Range API supports this natively); offsets are mapped back via a per-unit array of each text node's flat-text start position, built once at registration and reused for O(1) hit-testing (`tokenAt()`) instead of re-walking the DOM per click/hover. A block larger than `MAX_UNIT_CHARS` (20,000 — guards against e.g. an entire article sitting in one `<div>`, or text directly in `<body>`) falls back to the old per-text-node unit for just that block, trading accuracy back for bounded tokenize() calls. `content.ts`'s `blockOf` (used for sentence/context extraction) and the highlighter's are the same exported function now, not two copies.
- Scan-on-demand (roadmap item 15): the extension does **nothing** to a page until the reader asks. `content.ts` loads on every page but only reads settings; `enable()` (highlighter, MutationObserver, click/hover/key listeners, popup/editor hosts, YouTube extras) runs only when `reconcile()` says so: `hostAllowed() && (scanRequested ?? settings.autoScan)`. `scanRequested` is a per-page-load, in-memory choice: `null` follows the `autoScan` setting (default **false**), `true` = the reader pressed 스캔, `false` = pressed 스캔 끄기 (stays off, even with autoScan on, until the page reloads; a manual scan likewise survives the setting being switched off). The toolbar popup (`action.ts`) drives it with `chrome.tabs.sendMessage(tabId, {dokhack: 'scan' | 'unscan' | 'status'})` (types `TabCommand`/`TabStatus` in `types.ts`; no `tabs` permission needed — the tab id alone suffices and `activeTab` already covers the popup), and re-reads `{active, allowed}` from the content script's reply: no reply = no content script there (restricted page, or a tab opened before the extension loaded) → "페이지를 새로고침한 뒤" hint; `allowed: false` = the per-site "이 사이트에서 사용" switch is off, which still overrides everything including autoScan. The `autoScan` checkbox exists in both the popup and the options page (`library.html`'s 스캔 설정); both write the same setting. The website bridge (`initSiteBridge`) is independent of scanning and stays registered on the site's own origin.
- Content scripts only READ chrome.storage.local. All writes go through background.ts `serial()` to avoid cross-tab races.
- Word status keyed by lowercase lemma. "unknown" is never stored. Capitalized PROPN tokens are skipped.
- A hover cue (`::highlight(mine-hover)`, painted via `Highlighter.setHover()` in highlighter.ts, driven by a throttled `mousemove` listener in content.ts reusing the click hit-testing) shows a word is clickable even when it has no status color — "known" words paint no status highlight at all otherwise, so without this they looked inert.
- The in-page word card (popup.ts) and the card editor (editor.ts) each live in their own closed shadow root. The popup shows a quick red-pen best-guess Korean gloss (`.gloss`, top KRDICT candidate) alongside the English dictionary definitions. Clicking "카드 만들기" (or pressing S) always opens the editor — a centered modal, detached from the word's position — where the reader picks which meanings to keep (Korean and/or English, filterable via 표시 언어 한국어/영어/둘 다), edits/expands the sentence (segmentBlock + expandSentence/collapseSentence in content.ts pull in or drop neighboring sentences), before `saveCard` fires. This editor is reused as-is for YouTube subtitle mining (roadmap item 7, below) — no editor changes were needed for that. A YouTube audio-clip + video-frame capture step is a separate, not-yet-built piece (roadmap item 11) — not the user re-recording their own voice, which an earlier pass at this file mis-described it as; corrected per the user directly.
- YouTube subtitle mining (roadmap item 7) needed almost no new code, because nothing in the architecture is page-specific: the highlighter already tokenizes *any* text node on *any* page via its generic MutationObserver, so once the reader opens YouTube's own "Show transcript" panel, its caption lines (`ytd-transcript-segment-renderer` elements, each holding a `.segment-timestamp` and a `.segment-text`) get highlighted, clicked, and mined exactly like any paragraph — confirmed against real transcript-panel markup. Two real gaps needed fixing, both in how a caption line differs from prose: (1) `.segment-timestamp` ("0:03") sits right next to the caption text with no guaranteed whitespace between them in the DOM, which would otherwise fuse into the line's first word when `highlighter.ts` concatenates a block's text — excluded via `SKIP_CLASSES` (`segment-timestamp`), the same mechanism `SKIP_TAGS` already uses for `<code>`/`<pre>`/etc. (2) Auto-generated captions have no sentence-ending punctuation and each line is its own block-level element (not sentences within one shared paragraph), so the normal `Intl.Segmenter`-per-block approach would only ever find one "sentence" (that single line) and the editor's "+ 앞/뒤 문장" buttons would have nothing to expand into — `content.ts`'s `segmentBlock()` special-cases `YTD-TRANSCRIPT-SEGMENT-RENDERER` blocks (`segmentTranscriptLines()`) to use sibling caption lines as the sentence list instead. One UX quirk worth knowing, not a bug: a transcript line is YouTube's own seek-to-this-moment button (`role="button"`), so a plain click on it seeks the video instead of opening the word popup — mining from a transcript needs **Alt+click**, the same fallback the extension already uses for words inside links/buttons elsewhere.
- YouTube subtitle mining, phase 2: `youtube.ts`'s custom transcript viewer (injected as `#secondary`'s first child, 단어장-styled) and subtitle bar (overlaid on `#movie_player`, synced to `<video>`'s `timeupdate`), modeled on Kimchi Reader's equivalent pair. Both are plain light-DOM elements, not a shadow root like popup.ts/editor.ts, specifically so the existing Highlighter/content.ts click pipeline mines their word text exactly like any other page's — no changes needed to either file's mining logic, only `segmentBlock()` in content.ts gaining a `transcriptContextFor()` check (from youtube.ts) so a word clicked in either surface still gets the right sibling-lines sentence context for the editor's "+ 앞/뒤 문장" buttons, the same problem roadmap item 7's original `segmentTranscriptLines()` solved for YouTube's own panel. Clicking a word in the subtitle bar also pauses playback by default (`pauseIfBarWord()`, called from `openWord()`) — otherwise the line moves on while you're still reading the lookup; the transcript panel doesn't pause, since it's meant to be browsed independently of what's playing. No transcript API is reachable from a content script (see Testing's PoToken note), so line data comes from harvesting YouTube's native transcript UI once per video. This whole feature was initially designed against markup the user pasted from Kimchi Reader and from a static YouTube snapshot, and nearly every detail of *how to trigger, read, and close YouTube's own panel* turned out wrong once tested live (via Claude in Chrome, in the user's real browser) — the pasted snapshot had been captured mid-load, before either UI had finished rendering, and separately, YouTube turns out to render transcript lines with two entirely different, unrelated markups depending on the video (both live-confirmed, same session): the older `ytd-transcript-segment-renderer` (`.segment-timestamp`/`.segment-text`, what item 7's original Alt+click mining already relies on) and a newer `transcript-segment-view-model` web component whose class names are hashed per build and unusable as selectors — its timestamp is just the segment's first child `<div>` and its text lives in a `span[role="text"]`. `SEGMENT_SELECTOR` and `extractSegment()` in youtube.ts query and parse both shapes everywhere a segment is read. Four real, live-confirmed fixes: (1) the description's "Show transcript" button exists in the DOM but is never actually laid out (`offsetParent === null`) until the reader expands the description, so clicking it is usually a no-op — the reliable trigger is the "Transcript" tab (`role="tab"`, `aria-label="Transcript"`) in the separate "In this video" panel, which is visible and clickable as soon as it exists; both are clicked when found, since a no-op click on the other is harmless. (2) YouTube can render *two* engagement panels holding the same segment list — seen both as two panels sharing the identical `target-id="engagement-panel-searchable-transcript"` (654 raw segments for 327 real lines) on the older UI, and, on the newer view-model UI, as `target-id` flipping between `"PAmodern_transcript_view"` and `"null"` across the two copies (i.e. `target-id` cannot be trusted to name *which* copy is live) — `harvestTranscript()` picks whichever copy has `visibility="ENGAGEMENT_PANEL_VISIBILITY_EXPANDED"` rather than trusting document order or `target-id`. (3) The panel's real close control is labeled the generic "Close", shared by every engagement panel on the page (comments, chapters, ads...), so it's looked up scoped to this specific panel's own header, not page-wide — and it has to be *clicked*, not just hidden: while this panel is open, YouTube puts `#secondary` into `position: fixed` spanning the full page width (presumably so panels can render as overlays), and a `display:none` on the panel element alone left that layout state stuck, visibly breaking the sidebar; clicking the real close button returns `#secondary` to its normal narrow-column layout. (4) `closeAnyOpenTranscriptPanels()`'s sweep originally identified a transcript panel purely by `target-id` text-matching `/transcript/i` — which, per fix (2) above, can be `"null"` on the exact panel that needs closing on the newer UI, silently skipping it and leaving YouTube's own native panel stuck open next to (or instead of) ours; it now *also* matches any expanded panel containing a `SEGMENT_SELECTOR` element, regardless of what its `target-id` says. (5) Closing a panel (clicking its real Close button, per fix (3)) flips its `visibility` to HIDDEN but does *not* remove its segment nodes from the DOM — confirmed live across a chain of SPA navigations (YouTube never reloads the page, so nothing else clears them either): the original harvest check (`document.querySelectorAll(SEGMENT_SELECTOR).length`) couldn't tell a genuinely fresh, current-video panel apart from the *previous* video's now-hidden-but-still-populated one, so on navigating to a second video it would immediately "succeed" by reading those stale hidden nodes — skipping the trigger click and wait loop entirely — and silently show the wrong video's transcript with no error. `harvestTranscript()` now requires a currently-**EXPANDED** panel (`findExpandedTranscriptPanel()`) before trusting any segments at all. That alone still wasn't enough, though (also live-confirmed): YouTube can carry the *same* transcript panel component over to a new video already EXPANDED, still showing the *previous* video's real, live segments — not hidden leftovers, a genuinely visible stale panel that just hadn't been repopulated yet. `harvestTranscript()` now unconditionally calls `closeAnyOpenTranscriptPanels()` *before* ever looking for an existing panel, so the trigger click that follows is always a real fresh open tied to the current navigation, never a no-op read of whatever was already sitting open. (6) Even with (5)'s fix, the same symptom (a stuck-open panel/bar still showing an earlier video's transcript, sometimes several navigations later) kept recurring intermittently — traced to `'yt-navigate-finish'` itself not always firing: reliable through a real click on an older `ytd-compact-video-renderer` link, but confirmed live to sometimes go missing after navigating via `yt-lockup-view-model`, one of YouTube's newer link component variants. When the event doesn't fire, nothing ever calls `teardown()`, and the stale panel/bar (plus their now-orphaned `timeupdate` listener, still bound to the shared, reused `<video>` element and still firing on every tick of whatever's now playing) sit there indefinitely with no way to recover short of a real page reload. `initYouTubeExtras()` now also polls `location.pathname + location.search` every second (`checkNavigation()`) as a backstop alongside the event listener — not a replacement for it, since the event still reacts immediately when it does fire, just a net for when it doesn't. This supersedes the original Alt+click-on-native-panel workflow whenever it successfully builds; if harvesting fails (no captions, or a non-English YouTube UI — the label lookups are by English `aria-label`), the extension falls back to nothing extra, and the reader can still mine the native panel via Alt+click exactly as before. Re-runs on every `yt-navigate-finish` (YouTube is an SPA; switching videos never reloads the page) via a generation counter that discards stale in-flight harvesting from the previous video.
- YouTube audio-clip + video-frame capture (roadmap item 11): three new `youtube.ts` exports alongside the existing four, all still keeping `video`/`lines` module-private. `timeRangeForLines(firstIndex, lastIndex)` turns a line-index range into `{startMs, endMs}` (next line's `startMs`, or `video.duration`, or a 4s fallback tail, whichever applies) — indices into `sentenceCtx.list` in content.ts are already indices into `lines[]` (same array `transcriptContextFor()` maps over), so no new index-translation layer was needed. `captureFrame()` is the confirmed-safe `drawImage`+`toDataURL()` recipe from the Testing section, wrapped with a `readyState` guard and returning `null` on any failure. `captureAudioClip(startMs, endMs, onProgress, signal)` is one function for both the initial capture and a re-record (the caller just passes new times): seeks the video, waits for a real `'seeked'` event, starts a `MediaRecorder` on `video.captureStream()`'s audio track, plays in real time until `endMs`, stops, and resolves the recorded blob — restoring the video's original `currentTime`/paused state afterward (so a reader who had it paused via `pauseIfBarWord` is left paused), honoring an `AbortSignal` for cancellation, and bounded by a 5s seek timeout. Captured blobs never touch `chrome.storage.local`/`MinedCard` directly — storing a blob inline there (as base64) was considered and explicitly rejected in favor of a dedicated IndexedDB store, to avoid both the ~33% base64 bloat and making the existing "rewrite the whole `cards` array on every write" pattern heavier per card. The store (`src/blobstore.ts`, new file, `putBlob`/`getBlob`/`deleteBlob`) lives in the background worker, not a content script — a content script's own `indexedDB.open()` is scoped to the *page's* origin (youtube.com), not the extension's — so a captured blob is handed over as a **base64 string** (`src/binary.ts`) via three new `Request` types (`storeBlob`/`getBlob`/`deleteBlob`, see `background.ts`) — not an `ArrayBuffer`/`Blob`, which this first shipped as: Chrome JSON-serializes extension messages, which turns both into `{}`, so a clip sent that way would have been stored as nothing (caught while building roadmap item 12's library preview, before the round trip had ever been exercised live — the Testing section below still records it as unconfirmed), and `MinedCard` only ever carries the resulting reference id (`audioBlobId`/`frameBlobId`/`clipStartMs`/`clipEndMs`, all optional, same precedent as `synced?`). In `content.ts`, `segmentBlock()` gained a `youtube: boolean` return field — `true` only on the `transcriptContextFor()` branch (never the native-panel Alt+click fallback, never a plain page) — threaded into `sentenceCtx.youtube`; this single flag is the sole signal `openEditor()` uses to decide whether to build `EditorData.youtubeCapture` at all (null hides the whole capture UI). A captured blob is pushed to IndexedDB *immediately* on capture, not deferred to the final "카드 저장" click (recording is already a committed real-time action — buffering it only in memory risks losing it if the editor dies before save), tracked in a closure-local ref object inside `openEditor()` (not module state, matching how its handlers are already rebuilt fresh per `open()`); `onSave` "claims" it onto the saved card, while `CardEditor.close()` now fires a new `onClose` handler exactly once on *every* exit path (Save, Cancel, ✕, backdrop click, and Escape — which previously had no cleanup hook of its own) that best-effort-deletes anything left unclaimed, so an abandoned recording never leaks in IndexedDB. In `editor.ts`, a new capture section (hidden unless `youtubeCapture` is non-null) shows the auto-captured frame with a retake button, the current clip range with ±0.5s nudge buttons on each end (plain pill buttons, no waveform/scrubber — same visual language as the existing expand/collapse buttons) and a "stale" indicator once the range changes after a clip's already recorded, and a record/stop button pair with a progress bar and an `<audio controls>` preview. While recording, the editor's own close/cancel/confirm controls are disabled and Escape is ignored (checked via a new `CardEditor.isRecording` getter) — stopping only ever happens through the section's own "중단" button, so "what happens if the reader closes the editor mid-recording" is structurally impossible through the UI rather than a case cleanup code has to handle (the `AbortSignal` plumbing remains as defense-in-depth regardless). Re-expanding/collapsing context (the existing "+ 앞/뒤 문장" buttons) recomputes and redisplays the boundary automatically via a new `onRangeRecalc` handler reading the same `sentenceCtx.before/after` state `expandSentence()`/`collapseSentence()` already maintain (neither needed to change) — but the *actual* saved clip only updates on an explicit re-record, by design, matching the user's own spec.
- Website navigation and card preview/edit (roadmap item 12). Before this the website was two disconnected pages (sign-in → review, with a bare meta-refresh at the root) with no way to move between them, and a saved card could only be deleted. Now `../web` has a shared nav (`src/nav.ts`: top bar on desktop, a bottom tab bar under 640px, since review happens on a phone) over three signed-in pages — 홈 (`index.html`, now the real root: due count + "복습 시작", card-based stats, recent cards), 복습, and 카드 (`cards.html`: search + 전체/오늘 복습/새 카드/익숙해짐 filters, master-detail preview/edit/delete, a full-screen sheet on narrow screens) — with the 복습 tab badged by today's due count (read from PostgREST's `Content-Range` total via `Prefer: count=exact`, no rows transferred). "익숙해진 카드" deliberately reuses the extension's own auto-promote bar (ts-fsrs Review state, ≥3 reps, 0 lapses; `cards-api.ts` `isMastered`, kept in sync by hand with `background.ts`'s `LEARNED_*`). Editing changes only `sentence`/`target_start`/`definitions` — never an FSRS field — and requires the card's highlighted word (`surface`) to still appear in the edited sentence, since that's how `target_start` is located. The extension side: the toolbar popup's second button is now "웹사이트 열기" (the site root = home) with a due-count badge fetched asynchronously via a new `dueCount` request (no badge if not linked/offline), the library page links back to the website, and each card there gets 미리보기/편집 alongside 삭제 — the preview is where a card's YouTube frame and audio clip (item 11) can finally be seen/played, read straight from IndexedDB (`blobstore.ts`'s `getBlob`, same extension origin, no messaging). Edits sync both ways, which needed a stable link between a local card and its website row: `pushCard` now asks for `Prefer: return=representation` and records the new row's id as `MinedCard.remoteId`; cards synced before that existed are matched by content (lemma + sentence + url, each website row claimed at most once, since the old duplicate-push bug could leave identical rows) in `linkRemoteIds()` — using the *pre-edit* sentence when an edit is what triggered the lookup. An extension-side edit (`updateCard` request) is applied locally immediately and marked `dirty` if the card was synced, then pushed fire-and-forget; `dirty` stays set if that push fails, and `syncEdits()` (run at the end of every 모두 동기화) pushes pending edits first and only then pulls website-side edits into local cards — skipping any `dirty` card, so a pull can never overwrite an edit that hasn't gone up yet. Deleting a card now also deletes its audio/frame blobs (it leaked them before); deletion itself is still one-sided — removing a card in either place leaves the other's copy. Audio/frames were not on the website at first; roadmap item 16 added that (Supabase Storage).
- No AI/LLM calls of any kind, and (as of the WordNet switch) no third-party network calls for word meanings at all — deliberately removed (see roadmap item 3's note) and not coming back. Word meanings come from two local, offline sources, both fetched lazily from bundled JSON and cached in memory: `krdict.ts`'s `lookupKorean()` (Korean gloss, from `static/krdict.json`) and `wordnet.ts`'s `lookupEnglish()` (English definitions, from `static/wordnet.json`, replacing dictionaryapi.dev — see Testing). Both are optional independently — either can come back empty with no effect on the other. Pronunciation is browser TTS only (`content.ts`'s `speak()`) — there's no bundled audio or IPA source anymore.
- Word meanings are a *heuristic*, not disambiguation, on both sides: `krdict.ts` and `wordnet.ts` each rank their candidates with the same Lesk-style approach — does the clicked word's sentence share lemmatized words with a candidate's stored definition? — plus a part-of-speech match bonus and a mild common-sense preference (KRDICT's 초급/중급/고급 level for Korean; WordNet's own frequency-of-use sense order for English). Both sides of the overlap comparison are lemmatized with the same wink-nlp tokenizer (`nlp.ts`'s `tokenize()`) so irregular forms ("felt"/"feels"/"feeling") actually line up, and both exclude the clicked word's own lemma from that comparison — otherwise a definition that happens to mention the headword itself (WordNet glosses often do) gets a free match in every sentence regardless of which sense is meant. `krdict.ts` also gets a first-listed-synonym bonus now (roadmap item 10, the direction wordnet.ts already got "for free" from WordNet's sense ordering — see below): each `Row`'s optional 5th element, `first`, is `1` if that English word was the *first* one listed in KRDICT's own translation field for that Korean word's sense ("run" in "run;dash;sprint") rather than a buried alternate, computed once at extraction time (`scripts/extract-krdict.mjs`) via `words.indexOf(w) === 0`. It's a flat `+1.5` nudge, small next to a real definition-overlap match (`+3` per shared word) so it only ever breaks ties or nudges close calls, never overrides actual context evidence — deliberately the narrower of the roadmap note's two suggested directions (the other, biasing against hand-picked generic Korean words like 하다, was left for later: it needs ongoing curation with an unclear stopping point, where this reuses structure KRDICT's data already has). `first` is optional specifically so the currently-shipped `static/krdict.json` (built before this field existed, confirmed by checking it directly — every row still has exactly 4 elements) keeps working unchanged, reading as `undefined`/no-bonus on every row until the file is regenerated from a fresh KRDICT dump (see Commands — the dump itself isn't available in this environment, so that regeneration is a step for whoever has it next, not done as part of this change).
- Account linking (library.ts's "복습 웹사이트" section) is opt-in and independent of mining — email OTP via Supabase Auth, called through background.ts's `requestLoginCode`/`verifyLoginCode`/`logout` handlers (never directly from a page). With no account linked, everything behaves exactly as before this feature existed: fully local, no network calls beyond lookup/tokenize. Once linked, `saveCard` additionally (fire-and-forget, outside the `serial()` write queue so it can never make a successful local save look like it failed) pushes the card to Supabase for the review website (`../web`) to schedule with FSRS. A card is marked `synced` locally only once that push actually succeeds, so "모두 동기화" (and a retry after a dead session gets cleared — see below) only ever pushes what's missing, never re-creates rows that already made it. The extension never runs FSRS itself; review only happens on the website. Both the toolbar popup and the options page link out to the review site directly (`REVIEW_SITE_URL` in `config.ts`), not just to the extension's own options page.
- FSRS review results feed back into 학습 중/알아요 status (roadmap item 9) — the one missing direction until now: a mined card already went extension → Supabase → scheduled/reviewed on the website, which writes its updated FSRS state back onto that same row (`../web/src/review.ts`'s `fromCard()`), but nothing ever read that back into the extension. `background.ts`'s `pullLearnedWords()` closes the loop: on the same "모두 동기화" click that pushes unsynced cards (the two run in parallel — independent directions, nothing for them to race over), it queries Supabase for distinct `lemma`s among cards with `state=eq.2` (ts-fsrs's `State.Review`, confirmed against the installed package rather than assumed — graduated out of the initial Learning phase), `reps>=3`, and `lapses=eq.0` (never once rated 다시/Again against it), then promotes each matching lemma from `learning` to `known` locally. Deliberately narrow and simple rather than tuned to ts-fsrs's own scheduling internals (no `stability`/`difficulty` weighting) — a nudge, not the only path to 알아요, and the threshold constants (`LEARNED_STATE`, `LEARNED_MIN_REPS`) are isolated for easy tuning later. Only ever promotes a lemma whose local status is currently exactly `learning` — never touches one already marked `known`/`ignored` by the reader, and never touches a lemma with no local status at all (e.g. its card was deleted locally after syncing). If multiple cards share a lemma (different sentences), *any* one of them meeting the bar is enough — mastering one real instance of a word is treated as a legitimate signal, not requiring every mined sentence for it to individually clear the bar. Manual-trigger only (the existing "모두 동기화" button), consistent with every other sync in this codebase being opt-in and reader-initiated rather than a background poll/alarm.
- Every Supabase fetch (OTP request/verify, token refresh, card push) is wrapped with an 8s timeout (`background.ts`'s `fetchWithTimeout`) — an unbounded hang here reads as "sync is stuck," not as a visible error. A refresh that comes back 400/401 (the refresh token is dead — expired, revoked, or already rotated by a concurrent refresh from another tab) clears the stored account instead of retrying the same dead token forever: an honest "signed out" beats a "linked" account that silently never syncs again.
- Message types are defined in src/types.ts (`Request`); add new ones there first.
- Seen status, page coverage, opt-in line pause, Anki zip export, word import, vocabulary sync and the website reader (roadmap item 17): see that item and the matching Testing paragraph at the end of this file.

Split phrasal verbs ("turn the lights off") are now also caught, via `findSplitParticle()`'s cheap bounded heuristic rather than real dependency parsing (which wink-nlp doesn't have) — scans a short run of DET/ADJ/NOUN/PRON tokens after the verb for the matching particle, up to `MAX_SPLIT_GAP` (4) words, bailing immediately on punctuation or a non-noun-phrase word in between; see Architecture and Testing for the full behavior and how it was verified. Three known false-positive/negative classes, all narrow and pre-existing rather than introduced by either the connector or split-verb work (see Testing): a literal, non-idiomatic reading can still wrongly merge ("ran up the stairs" → "run up," WordNet's *accumulate* sense — this applies equally to a split reading like "ran the stairs up"); a word wink-nlp mistags as a proper noun at the start of a sentence (e.g. "Due" in "Due to...") is dropped before merging ever gets a chance, the same as any standalone word would be; and a phrase containing a possessive ("call one's bluff") still can't merge either way — `tokenize()` drops possessive "'s" as a contraction piece, so the word count never lines up.
5. ~~Tokenize per block element instead of per text node~~ — done: see Architecture's "Tokenizing happens per block-level element" bullet. `highlighter.ts` now finds each block once (`blockOf()`), tokenizes its whole flattened text in one call, and maps tokens back onto (possibly several) text nodes via each node's flat-offset start — verified against jsdom + wink-nlp (see Testing). Bonus: this is also what lets item 4's phrasal-verb merging catch a phrase split by inline markup ("give <em>up</em>"), which per-text-node tokenizing structurally couldn't.
6. ~~Own English→Korean dictionary data~~ — done, and it's what replaced item 3's AI gloss: `static/krdict.json`, a ~49,000-word English→Korean reverse index built by `scripts/extract-krdict.mjs` from KRDICT's (국립국어원, CC BY-SA) full bulk data dump — not the kaikki.org Wiktionary extracts this item originally named, which turned out unneeded once KRDICT panned out. `src/krdict.ts` ranks candidates locally with a Lesk-style heuristic (see Architecture) — no network call, no AI. The English side got the same treatment once dictionaryapi.dev turned out unreliable (see Testing): `static/wordnet.json`, a ~78,000-word index built by `scripts/extract-wordnet.mjs` from Princeton WordNet (bundled via the `wordnet-db` npm package — no separate download, unlike KRDICT), ranked by `src/wordnet.ts` the same way. `wordlist.ts`'s frequency bands (roadmap item 1) are a separate dataset and weren't extended by either; still hand-built.
